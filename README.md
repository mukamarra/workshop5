# Лабораторна робота №5: Реалізація REST API з реляційними зв'язками за допомогою TypeORM

## 1. Опис сутностей та зв'язків
У проєкті інтегровано дві пов'язані сутності з курсової роботи:
* **Category (Категорія)** — містить інформацію про категорії товарів.
* **Product (Продукт)** — містить інформацію про конкретний товар (назва, ціна) та прив'язку до категорії.

**Зв'язок між сутностями:** Реалізовано реляційний зв'язок **One-to-Many / Many-to-One** (Один-до-багатьох). Одна категорія може містити багато продуктів, але один продукт належить виключно одній категорії. У таблиці продуктів створено зовнішній ключ `category_id`.

---

## 2. Перелік реалізованих API ендпоінтів

| Метод | Ендпоінт | Опис | Доступ |
| :--- | :--- | :--- | :--- |
| **POST** | `/v1/auth/login` | Аутентифікація користувача та отримання JWT-токена | Публічний |
| **POST** | `/v1/products` | Створення нового продукту | Авторизований |
| **GET** | `/v1/products` | Отримання списку всіх продуктів (**з виконанням SQL JOIN**) | Авторизований |
| **GET** | `/v1/products/:id` | Отримання детальної інформації про один продукт за ID | Авторизований |
| **PUT** | `/v1/products/:id` | Оновлення даних продукту за ID | Авторизований |
| **DELETE**| `/v1/products/:id` | Видалення продукту за ID | Авторизований |

# Лабораторна робота №6: Впровадження сервісного шару, валідації та DTO

## 1. Пояснення ролі кожного архітектурного шару
У ході рефакторингу додаток було розділено на 4 ізольовані шари (Separation of Concerns):
* **Middleware (Валідація):** Перехоплює вхідний HTTP-запит до того, як він потрапить у контролер. Перевіряє наявність полів та коректність типів даних. У разі помилки відхиляє запит із кодом 400.
* **Controller (Оркестрація):** Відповідає суто за HTTP-рівень. Він приймає запит, передає дані в сервіс, отримує результат, загортає його в DTO та відправляє клієнту відповідь. Не містить бізнес-логіки та не працює з БД напряму.
* **Service (Бізнес-логіка):** Клас, який містить чисту логіку додатка. Він керує процесами та взаємодіє з репозиторієм бази даних.
* **Repository (Доступ до даних / Entity):** Рівень TypeORM, який відповідає за генерацію SQL-запитів та безпосередню роботу з таблицями PostgreSQL.

## 2. Приклади реалізованого коду
Код моєї middleware-функції валідації, ResponseDTO та сервіс-класу повністю завантажено в репозиторій у відповідні папки (`src/middleware/`, `src/dto/`, `src/services/`).

## Лабораторна робота №8-9: Full-stack інтеграція з REST API

### 1. Короткий опис функціоналу
Реалізовано клієнтську частину додатка для інтеграції з Express-бекендом. Забезпечено завантаження та відображення реляційних даних (SQL JOIN), клієнтську валідацію форм через Zod та збереження стану через TanStack Query.

### 2. Приклади ключового коду
* Конфігурація Axios (`src/lib/axios.ts`) для автоматичного прокидання токенів.
* Кастомні хуки TanStack Query (`src/features/products/api.ts`).
* Схема валідації Zod (`src/routes/products/$productId.tsx`).
Усі файли завантажено у відповідні директорії репозиторію.
